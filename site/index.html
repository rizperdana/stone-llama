CLI · local model server · EXL3

stone-llama

An ollama-style CLI and local OpenAI-compatible model server for ExLlamaV3 + TabbyAPI, built for very low spec machines — the reference card is an RTX 3050 Laptop with 4096 MiB VRAM. One static Go binary, zero third-party dependencies (go.mod has no require, no go.sum).

  • VRAM-aware autofit. Computes the largest safe context and KV cache mode from your GPU and the model’s own config.json, prints the arithmetic (weights + KV + overhead against your VRAM), and warns when the margin is thin — a maxed-out context can OOM during prefill on a used card, before a single token is generated.
  • Pre-download fit gate. fit and the gate inside pull decide architecture → quant format → fit from HuggingFace metadata alone — a few KB in the usual case, ≤ ~16 MiB worst case per repo — before any weight byte moves, and refuse with the numbers — including the largest context that would fit.

Commands: doctor, setup, fit, pull, rank, list, serve, ps, stop, run, version, rm, import, login.

curl -fsSL https://raw.githubusercontent.com/rizperdana/stone-llama/main/scripts/install.sh | sh

Install with the one-line installer (SHA-256 verified against the release’s combined checksums.txt) or build from source: docs/INSTALLATION.md. A pre-release, v0.1.0-rc1, is published.

01 — the two mechanisms

What it does that a stock config cannot

Both decisions run before you commit bandwidth or VRAM: one decides how much context your card can actually hold, the other whether the model belongs on it at all.

VRAM-aware autofit

Everything comes from the model’s own config.json plus your VRAM:

head_dim  = hidden_size / num_attention_heads
elems/tok = num_hidden_layers × 2 × num_key_value_heads × head_dim
load_mib    = weights_mib + ctx × elems/tok × bytes_per_element/2²⁰ + 128
headroom_mib(ctx) = 512 base + 512 prefill workspace [est] + 512 × ctx/65536 [est]
fits ⟺ load_mib ≤ vram_total_mib − headroom_mib(ctx)

Cache cost per token: FP16 2 B, Q8 1 B, Q4 0.5 B per element. The ladder tries ctx at the trained max, halves it down to 4096, and prefers better cache quality at each tier; it never exceeds max_position_embeddings. Flags (--ctx, --cache-mode, --no-autofit) always win, and the decision plus its arithmetic is always printed. fit also prints predicted decode/prefill tok/s [est] from metadata — that arithmetic lives with the model table.

Max context can OOM during prefill

On a 4 GB card a maxed-out max_seq_len can leave so little VRAM that prefill OOMs on agent-sized prompts — measured failure at ~2.5k tokens with ~20 MiB free; 65536 context at Q4 KV reserves ~1.15 GiB of the card before a single token exists.

CUDA OOM before the first token is this caveat: lower --ctx one tier (32768 → 16384). The ladder default is the safe context; explicitly passing --ctx 65536 buys the max context and prints what it costs.

Pre-download fit gate

fit — and the same gate inside pull — decides from metadata alone before a single weight byte moves: config.json, the quant config, the file tree, and the safetensors headers — at most 4 files, one ranged GET each, with header_size validated and capped at 4 MiB before any allocation (≤ ~16 MiB worst case per repo; bodies closed as soon as the header parses). If a header cannot be read — gated, missing, oversize, transport error — the format verdict is warn / unverified: never a silent pass, never a refusal for failing to look. Three checks:

  1. Architecture — config.architectures[] must be one the installed exllamav3 declares; unknown → warned, never silently accepted.
  2. Quant format — quant_method must be exl3; exl2 → refused; GGUF-only repo → refused with “use ollama with GGUF”; quant-group tensor dtypes must be loadable by the installed engine, as read from the safetensors headers.
  3. Fit — proceed, proceed-with-warning (smaller ctx), or refuse — with numbers either way, plus the largest ctx that would fit.

For scale, a real catch: a live 1.68 GB repo whose quant tensors are a dtype the installed engine cannot load (unsigned int16 .trellis) is refused before the consent prompt, naming the dtype and the engine limitation — the previous gate accepted it as gate: quant ✓ exl3 and would have downloaded it all.

≤ ~16 MiB of metadata worst case per repo — a few MB in practice, a few KB in the usual one — still two to three orders of magnitude below the smallest candidate model (1.68 GB). That bound is what turns a wasted multi-GB download into a metadata read. The verdict is saved to the model’s manifest.json and shown by list.

Where stone-llama loses

  • No CPU, AMD, or Apple inference, and Linux/amd64 is the only supported platform (Windows binary published, untested at runtime). Every other tool here runs on CPU.8
  • One loaded model at a time — no concurrent multi-model serving. ollama budgets OLLAMA_MAX_LOADED_MODELS, LM Studio auto-evicts.13
  • No keep-alive or idle auto-unload: a loaded model stays resident until stop (only manual /-/unload). ollama’s keep_alive and LM Studio’s TTL/Auto-Evict unload idle models.139
  • EXL3 only: no GGUF, no EXL2, no draft/speculative models — while GGUF is what most tools in this table serve.8
  • No training or fine-tuning of any kind — serving only; there is no such command. For training/quantisation you need an adjacent tool (below).8

05 — model compatibility

What fits a 4 GB card, and how fast

Metadata-only ranking from 2026-09-26 — HF API, config.json, safetensors headers; zero weight bytes downloaded. Machine: RTX 3050 Laptop, 4096 MiB, budget weights + KV ≤ 3508 MiB. Ratings 1–5 with 3 = SmolLM3-3B baseline.

Decode on these models is bandwidth-bound — each token streams the weights plus the KV bytes for your context through VRAM once — so every predicted tok/s is arithmetic:

tok/s ≈ effective bandwidth ÷ bytes read per token

The ≈83.6 GB/s constant is calibrated to the measured 42.7 tok/s SmolLM3-3B 3.5 bpw point (1,957,008,720 B) on this card — the one measured number here; everything else carries [est] until calibration lands. A prediction is relative to the chosen context: bigger ctx streams more KV bytes per token (SmolLM3 at 65,536 ctx Q4 reads ≈1152 MiB of KV per token, ≈26 tok/s ceiling [est]), so rows quoted at different contexts are not comparable. fit prints both decode and prefill predictions.
