stone-llama

Ollama-style CLI and local model server for ExLlamaV3 + TabbyAPI — one Go binary that pulls EXL3 models, auto-fits context to your VRAM, and serves an OpenAI-compatible API.

Commands in a source build today: doctor, setup, fit, pull, rank, list, serve, ps, stop, run.

curl -fsSL https://raw.githubusercontent.com/rizperdana/stone-llama/main/scripts/install.sh | sh

Release pending: the one-liner installs the latest published release — none is published yet, so it fails with “could not determine latest release version”. Until the first release lands, build from source: docs/INSTALLATION.md, Option B.

02 — before any download

Fit and gate decide from metadata

fit — and the same gate inside pull — reads only a few KB of HuggingFace metadata (config.json, quant config, file tree) and decides before a single weight byte moves.

Auto-fit context

stone-llama computes the largest safe context and cache mode from your GPU and the model’s own config.json, and prints the arithmetic. Flags (--ctx, --cache-mode, --no-autofit) always win. Cache cost per token: FP16 2 B, Q8 1 B, Q4 0.5 B per element. If nothing fits, you get the breakdown plus the largest context that would fit — before anything downloads.

Pre-download gate

  1. Architecture — config.architectures[] must be one the installed exllamav3 declares; unknown → warned, never silently accepted.
  2. Quant format — quant_method must be exl3; exl2 → refused; GGUF-only repo → refused with “use ollama with GGUF”.
  3. Fit — proceed, proceed-with-warning (smaller ctx), or refuse — with numbers either way.

~2 KB of metadata is the cost of a caught mistake instead of a wasted multi-GB download.

03 — platform limits

NVIDIA-CUDA only. Read this first.

exllamav3 — the inference engine stone-llama wraps — has no CPU path, no AMD/ROCm path, no Apple/Metal path. Not configurable.

Linux/amd64 is the only supported platform in v1. On CPU/AMD/Apple, use ollama with GGUF instead. stone-llama doctor prints this verdict — with your GPU and driver numbers — before anything gets installed.

Max context can OOM during prefill

On a 4 GB card a maxed-out max_seq_len can leave so little VRAM that prefill OOMs on agent-sized prompts — measured failure at ~2.5k tokens with ~20 MiB free; 65536 context at Q4 KV reserves ~1.15 GiB of the card before a single token exists.

CUDA OOM before the first token is this caveat: lower --ctx one tier (32768 → 16384). The ladder default is the safe context; explicitly passing --ctx 65536 buys the max context and prints what it costs.

04 — model compatibility

What fits a 4 GB card, and how fast

Metadata-only ranking from 2026-09-26 — HF API, config.json, safetensors headers; zero weight bytes downloaded. Machine: RTX 3050 Laptop, 4096 MiB, budget weights + KV ≤ 3508 MiB. Ratings 1–5 with 3 = SmolLM3-3B baseline.

Decode on these models is bandwidth-bound — each token streams the weights plus the KV bytes for your context through VRAM once — so every predicted tok/s is arithmetic:

tok/s ≈ effective bandwidth ÷ bytes read per token

The ≈83.6 GB/s constant is calibrated to the measured 42.7 tok/s SmolLM3-3B 3.5 bpw point (1,957,008,720 B) on this card — the one measured number here; everything else carries [est] until calibration lands. A prediction is relative to the chosen context: bigger ctx streams more KV bytes per token (SmolLM3 at 65,536 ctx Q4 reads ≈1152 MiB of KV per token, ≈26 tok/s ceiling [est]), so rows quoted at different contexts are not comparable. fit prints both decode and prefill predictions.
