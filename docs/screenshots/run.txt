Attach mode owns no model load — by design:

    POST /-/load   (Authorization: Bearer <daemon state token>)
    → HTTP/1.1 409 Conflict   type: attach_mode
      "attach mode: model loading is owned by the upstream server — …"
      (internal/serve/load.go, handleLoad)

The raw curl capture this note replaces (26 Sep 2026) printed a request
with NO Authorization header and showed `HTTP/1.1 409 Conflict`. That is
no longer reproducible as printed: since the Host/Origin/bearer gates
landed, `/-/load` is a control route and answers **401 `unauthorized`**
to any request without the state token (`daemon.json`, 0600). The
capture's message text has also since been rewritten in `load.go`, and
the `raw/` files it cited are not in this tree. No new transcript is
claimed here — there is no live supervised daemon to re-capture one (it
needs the provisioned runtime, never authorized on this machine), and
fabricating terminal output would break the repo's verbatim-output rule.
The 409 `attach_mode` contract itself is unchanged.

`$ stone-llama run SomeOtherModel -p hi` → `exit=1` above is historical
too: `internal/cli` now reports a name mismatch as a local alias and
reuses the upstream's loaded model instead of failing.

With the model name that the upstream actually has loaded, `run` never
calls `/-/load` at all — there is nothing to load in attach mode.

Supervised (non-attach) `serve` and its `/-/load` SSE success stream were
NOT exercised: they need the provisioned Python runtime (`stone-llama
setup`, ~5.6 GB, never authorized on this machine) plus a second model
load contending for the same 4096 MiB card. Known untested path, not a
claim of support.
